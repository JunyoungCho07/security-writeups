# Session 2026-09-28 — shellcode 주입, 그리고 에이전트 과잉의 교정

## 0. 세션 성격

전날 첫 pwnable 을 푼 직후의 연속 세션. 두 번째 문제는 **점프할 기존 함수가 없어** 코드를
직접 주입해야 했고, JY 는 **x86-64 어셈블리를 이 세션에서 처음 썼다.** 해결.

§1.4 유지 — payload·offset·정답 미제공. 다만 §4 참조: **도구를 대신 만든 것이 이 세션의
가장 큰 프로세스 실패였다.**

## 1. 해결 ✅

전날 세운 **네 링크 프레임이 값을 했다.** 두 문제의 차이가 "④ 목적지 실행" 하나로 즉시
정리됐고, 그 하나가 바뀌면서 전제 두 개가 새로 붙었다:

1. **스택에 실행 권한** — program header 의 `STACK` 세그먼트 flags
2. **스택 주소를 알 것** — 프로그램이 스스로 출력해 준다

⭐ **두 번째가 JY 가 놓쳤던 지점이다.** `e_type` 이 No PIE 라는 것을 읽고 "주소 고정"으로
결론냈는데, 그건 **실행 파일 본체**에만 해당한다. 같은 프로그램을 3회 실행해 `[stack]`
베이스가 매번 다른 것을 측정해 보여주니 교정됐다. ASLR 은 손잡이가 여러 개다.

그리고 JY 가 "스택이 rwx 니까 코드 주입하는 문제겠네"로 바로 건너뛰려 했을 때 **가능 ≠
필요**를 지적했다 — 선물 함수가 남아 있으면 그쪽이 훨씬 싸므로, 방어 기제가 아니라
**소스와 심볼**이 공격 형태를 정한다. 소스를 보니 그 함수가 제거돼 있어 그의 직감이 결과적으로
맞았지만, **맞은 이유가 달랐다.**

## 2. 어셈블리를 0에서 — 올라간 순서

JY 는 어셈블리를 써 본 적이 없었다. 한 걸음씩:

| 단계 | 새로 배운 것 | 검증 |
|---|---|---|
| `exit(N)` | syscall 번호·인자 레지스터, `.s` 파일 구조 | 종료 코드 |
| `write(1, rsp, N)` | `rsi` 는 **글자가 아니라 주소**를 받는다 | 쓰레기 출력 |
| `push <1글자>` | 스택에 값을 놓으면 `rsp` 가 그 주소 | 글자 출력 |
| `push <2글자>` | **리틀엔디안** | 두 글자 출력 |
| `movabs` + `push rax` | `push` 는 상수 4바이트까지 | 문자열 출력 |
| `execve` | 레지스터 재배치만 | shell |

⭐ **중간 단계로 `write` 를 거친 것이 결정적이었다.** "문자열이 그 주소에 있나"와 "execve 가
맞나"를 동시에 디버깅하지 않아도 됐다. **한 번에 하나만 틀리게 만들기.**

JY 가 두 글자 출력을 처음엔 **`write` 2회**로 풀었다 — 유효하지만 글자당 28바이트로
확장 불가. 비용을 숫자로 보여주자 한 `push` 로 재작성하며 **리틀엔디안을 스스로 발견**했다.
그 다음 8바이트에서 `push` 의 imm32 한계에 부딪히고 `movabs` 로 우회.

## 4. 🔴 에이전트 오류 — 정직하게

### 4.1 가장 큰 것: 도구를 대신 만들었다

빌드 스크립트, 테스트 하니스(`runsc.c`), Dockerfile, 쉘 헬퍼 5개, exploit 뼈대를 **내가
작성했다.** JY: *"그렇게 너가 다 만들면 내가하는 의미가 없잖아 bof2 쉘 스크립트도 bin도 다
내가 작성해야하잖아."*

전부 삭제하고 그가 쓴 `.s` 파일 둘만 남겼다. **§1.4 는 답을 금지하지만, 도구를 대신 만드는
것은 같은 학습을 뒷문으로 제거한다.** pwn 에서 도구를 짜는 것 자체가 실력이다.
→ 에이전트 메모리 `feedback-keep-it-minimal` 신규.

### 4.2 정보량 과잉 — 두 번 제동이 걸렸다

*"너무 수준이 대학원수준이다"*, *"내 수준을 너무 뛰어넘는다 ... 좀 쉽게 가자 ㅈㅂ"*,
그리고 마지막에 *"최대한 간단하게 유지하라 ... 정말 간단한 명령들로 exploit 하는것이 맞지"*.

표 5개 + 검증 탠젠트 3개짜리 답변이 반복됐다. **그가 다음 한 걸음을 못 찾는 상태**였는데
세 걸음 뒤까지 설명했다.

### 4.3 잘못된 일반화 — `objcopy`

`readelf` 가 arm64 컨테이너에서 x86-64 ELF 를 읽는 것을 보고 **"구조 작업이니 `objcopy` 도
된다"고 말했다.** 틀렸다. `objcopy`/`objdump`/`nm` 은 **BFD** 경유라 타깃 게이트가 걸리고,
`readelf` 만 독립 파서다. JY 가 실제로 그 에러(`Unable to recognise the format`)를 맞고 나서
정정했다. 하나를 보고 전체로 일반화한 것 — 전날 objdump 플래그 오류와 같은 패턴이다.

### 4.4 무효한 측정을 "보너스"로 제시

`GNU_STACK` 플래그가 실제 페이지 권한이 되는지를 `/proc/<pid>/maps` 로 보여주려 했는데,
**qemu-user 아래서는 QEMU 자신의 맵이 나온다** (호스트 arm64 주소 형태가 증거). 두 번 시도해
두 번 다 무효였고, 철회했다. 원래 주장은 **미검증으로 남겼다** — 파킹 대신 이 로그에 남긴다.
얻은 것: **에뮬레이션 아래 동적 메모리 관찰의 한계**라는 더 일반적인 사실.

### 4.5 불필요한 우회를 만들었다

바이트 추출에 도커를 끌고 갔다(`readelf` 때문). 실제로는 호스트 `objdump -s -j .text` 로
끝났다. **전날 스스로 세운 "정적 분석은 호스트" 원칙을 내가 어겼다.**
그리고 그 출력을 grep/cut/tr 로 파싱하는 4단계 파이프라인을 가르치려 했는데, JY 가 정규식에
막혔다. **실제 해법은 `bytes.fromhex()` 에 hex 를 붙여넣는 것**이었다 — 1초. 배울 가치가 낮은
곳에서 시간을 쓰게 했다.

## 5. 도구 정책 변경 — pwntools 도입

전날 JY 가 정한 조건: *"pwntools 는 bof234 도 쌩으로 해보면서 기초원리에 익숙해지고 툴을
쓰자"*, 도입 신호는 **그 자신의 지루함.**

**그 신호가 왔다** — 수동 경로가 pwn 이 아니라 쉘 텍스트 처리로 변질된 지점에서 JY 가 직접
요청했다. 그 시점까지 손으로 해낸 것: 어셈블리 shellcode, 문자열 리틀엔디안 패킹,
디스어셈블리에서 offset 유도, ELF 에서 방어 기제 4개 판독. **가려질 것이 이미 학습된 뒤.**

계속 제외: `checksec`, `shellcraft`, 자동 ROP, one_gadget, angr — **무엇을 할지 결정하는**
자동화.

설치 함정(측정): `pip install pwntools` 가 `unicorn` 소스 빌드로 넘어가 `cmake` 없음으로
실패한다. 원인은 pwntools 가 허용하는 가장 높은 unicorn 버전만 해당 플랫폼 wheel 이 없기
때문. wheel 있는 버전을 함께 지정하면 해결. 그리고 `ModuleNotFoundError: No module named
'pwn'` 은 **인터프리터 불일치**였다 — pyenv 쪽에만 깔렸고 시스템 Python 으로 실행했다.

## 6. Struggle points

- **오프셋 계산에서 두 번 막혔다.** "인덱스가 몇인지 모르겠다" → 작은 버퍼(4바이트)로
  인덱스를 전부 나열해 보여주니 규칙(`버퍼 크기 + 8`)을 스스로 일반화했다. 큰 수로 설명한
  것이 문제였다.
- **`rsp` 위치를 안 말하고 배치 안전성을 설명했다.** "낮은 주소에 있어서 안전"이라고만 썼는데
  JY: *"이해 안됨"*. 맞다 — 안전의 근거는 방향이 아니라 **거리**이고, 그러려면 `ret` 직후
  `rsp` 가 어디인지를 먼저 말해야 했다.
- **`od`/`printf` 같은 기본 도구를 모르는 상태**가 여러 번 드러났다. 이미 아는 값(`h`=0x68)
  으로 대조해 보여주는 방식이 잘 통했다.
- exploit 첫 버전에 버그 3개가 한 줄에 몰려 있었다 (슬라이스 위치, `str(bytes)`, 바이트 순서).
  셋 다 **에러 없이 틀린 결과**를 내는 종류. 실제 값으로 각각 재현해 보여주니 바로 고쳤다.
