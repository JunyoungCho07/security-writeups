# Session 2026-09-29 — 첫 ROP, 좌표계, 그리고 프레임이 혼자 작동했다

> 2문제 해결. §1~7 은 첫 번째(ret2libc), §8~15 는 두 번째(canary, **JY 단독**).

## 0. 세션 성격

전날 shellcode 주입을 푼 직후의 연속 세션. 세 번째 문제는 **NX 가 켜져** 주입 코드가 죽었고,
목적지를 공유 라이브러리에서 찾아야 했다. JY 의 **첫 ROP·첫 ret2libc.** 해결.

§1.4 유지 — payload·offset·정답 미제공.
**§1.4 확장 규칙(2026-09-28 신설)도 유지: 이 세션에서 에이전트는 `.py`·스크립트·설정 파일을
하나도 쓰지 않았다.** JY 가 exploit 전부를 직접 작성했고 에이전트는 개념·환경 사실·코드
리뷰만 했다. 전날의 프로세스 실패가 재발하지 않았다.

## 1. 해결 ✅

**④ 만 바뀐다는 프레임이 세 번 연속 맞았다.** ret2win → ret2shellcode → ret2libc 에서
①②③이 동일. 그런데 이번에는 프레임 자체가 확장됐다:

> ⭐ **링크 ⓪ — 주소 확보(leak)** 를 새로 분리했다.

NX·ASLR 이 켜지면 ④ 의 목적지가 실행마다 움직이므로, payload 를 만들기 **전에** 주소를
알아내는 단계가 생긴다. ret2win 에는 없던 링크다(주소가 파일에 고정). 그리고 **실전 문제의
난이도는 대체로 ④ 가 아니라 ⓪ 에 있다** — leak 이 공짜로 주어지는가, 2단계 체인으로 스스로
만들어야 하는가. `MOC_Binary_Exploitation` 의 The Chain 표에 5번째 행으로 올렸다.

JY 가 스스로 도달한 것:
- 판독 4개 중 PIE·NX·RELRO 를 정확히 읽고 **"이 공격에" 분류**까지 (§3 의 [Nullity] 함정 제외)
- `base = leak − off` / `target = base + off` 를 **질문받기 전에 먼저 말했다**
- 체인 슬롯 구조 (`pop` 이 먹는 값 + `ret` 이 먹는 값의 순서)
- offset = 버퍼 크기 + 8 을 디스어셈블리로 확정

## 2. ⭐ 이번 세션의 두 통찰

**① CPU 는 함수 경계를 모른다.** 정렬 보정용 빈 `ret` 가젯이 필요해졌을 때, 그것이
**이미 있던 가젯의 두 번째 바이트**였다. 가젯 주소 + 1 에서 시작하면 `pop` 이 사라지고 `ret`
하나만 남는다. 디스어셈블러가 그려주는 명령 경계는 *한 가지 해석*이고, CPU 는 주어진 주소의
바이트를 그 자리에서 디코드한다. **이것이 ROP 가 성립하는 근본 이유**이고, 가변 길이 명령인
x86 에 가젯이 넘쳐나는 이유다.

**② 같은 파일에 대해 도구들이 다른 좌표계로 답한다.**

| 출처 | 좌표계 |
|---|---|
| 심볼표 (`nm`) | 가상 주소 — `ET_DYN` 이면 base 상대, `ET_EXEC` 이면 절대 |
| `strings -t x` | **파일 오프셋** |
| `objdump -d` 왼쪽 | 가상 주소 |

세 종류가 한 payload 에 들어가는데 **형식이 똑같이 16진수**라 섞이면 조용히 틀린다.
`PT_LOAD` 변환을 손으로 해봤고, "libc 는 `strings` 오프셋 그대로 쓰면 된다"는 통설의 반례가
**같은 파일 안**에 있는 것을 확인했다(`rw-` 세그먼트는 한 페이지 어긋나 있다).

## 4. 🔴 에이전트 오류 — 정직하게

### 4.1 정렬 설명이 또 너무 밀도 높았다

1차 설명에서 `R ≡ 8 (mod 16)` 표기와 mod 산술로 갔다. JY: **"왜 안된건지 모르겠는데"**.

재구성: `mod 16` 추적을 버리고 **"슬롯 개수의 홀짝"** 으로 바꿨다 — 등가이면서 payload 작성에
직결된다(`p64` 개수를 세는 것과 같다). 이 형태로는 바로 통했다.

🔴 **전날과 같은 실패 모드다.** 어제는 `push` 방향 설명에서 "이해 안됨"이 나왔고 거리로
재구성해서 풀렸다. 공통점: **정확하지만 추상적인 형태를 먼저 내놓았다.** 교훈은
"수식보다 세는 법" — JY 에게는 **계산 절차**가 관계식보다 먼저 와야 한다.

### 4.2 🔴 공개 노트에 실제 문제 오프셋을 썼다

`Tools/nm` 에 `nm -D` 출력 예시를 **실제 libc 오프셋 그대로** 넣었고, `Tools/strings`·
`Binary_Number_Encoding`·`Ret2Libc_Pattern` 에도 실제 값(문자열 오프셋, 가젯 주소, leak 의
하위 3자리)이 들어갔다. 4개 파일.

**커밋 전 자체 스캔에서 잡아 합성값으로 전량 교체**했고, 유도값(정수 표기, 리틀엔디안 바이트
나열)까지 새 값에 맞게 재계산했다. 재스캔 clean.

🔴 **전날의 `0x200` 건과 같은 계열이고 규모가 더 크다.** 원인 진단: 측정값을 예시로 쓰면
설명이 구체적이고 좋아지는데, **그 구체성이 곧 유출**이다. 교정: 공개 노트의 예시는
**처음부터 합성값으로 쓴다** — 나중에 치환하지 않는다. 치환은 유도값 불일치를 남긴다.

### 4.3 바이트 주소 통찰을 어디까지 줬나 — 판단 기록

가젯+1 이 빈 `ret` 라는 것을, JY 가 두 번 막힌 뒤에 **디스어셈블리 두 줄을 다시 제시하고
"두 바이트가 각자 주소를 갖는다"까지** 말했다. 체인 내 배치는 그에게 남겼다.

§1.4 경계선상이다. 판단 근거: ① 그것은 *그의 출력물*에 대한 사실 판독이고 ② 문제의 답이
아니라 CPU 동작의 일반 사실이며 ③ 두 번 막힌 상태에서 범위를 한 행동으로 줄이는 것이
2026-09-28 메모리에 기록된 방침이다. **기록해 두고 다음 세션에 재평가한다.**

## 5. Struggle points

| 지점 | 실제로 일어난 일 |
|---|---|
| 정렬 | 2라운드 필요 (§4.1). JY 의 첫 추측은 "전 문제는 강제 정렬이었나" — 오답 |
| **정수 / 텍스트 / 바이트** | **2세션 연속.** 오프셋을 `b'000…'` 로 쓰고 `int.from_bytes` 로 읽었다. 에러 없이 천문학적 값이 나온다 |
| python 16진 리터럴 | 앞자리 `0` 패딩을 그대로 복사 → `SyntaxError`. 도구 출력이 0-padded 인 것이 원인 |
| `to_bytes(2, 'big')` | `OverflowError` — 주소는 8바이트 리틀엔디안. `p64` 의 존재 이유 |
| payload 를 안 보냄 | `print(payload)` 만 있고 `send`/`interactive` 없음. 코드 리뷰에서 지적 |
| leak 줄 파싱 | 토큰 인덱스가 전 문제와 달랐다. `print(.split())` 로 직접 확인하게 유도 |
| canary 판독 | `U` 를 숨기는 플래그로 목록을 뽑아 "없음"으로 결론. **결론은 맞고 증거는 깨졌다** |

⭐ 마지막 항목이 이 세션의 방법론적 수확이다: **"없음"을 증거로 쓰려면 먼저 그 방법이
"있음"을 보여줄 수 있는지 확인해야 한다.** `Memory_Protections` §D 와 `Tools/nm` Pitfalls 에
[Nullity] 블록으로 기록.

# Session 2026-09-29 (2차) — canary, 그리고 프레임이 혼자 작동했다

## 8. 같은 날 두 번째 해결 ✅ — **JY 단독**

네 번째 문제를 **JY 가 혼자 풀었다.** 에이전트는 개념 설명도, 힌트도, 코드 리뷰도 하지 않았다.
풀고 난 뒤 질문 하나만 왔다: *"패딩이 왜 필요한지 설명해주고 eol가자. 패딩 안하면
exploit안되었었다."*

⭐ **1~3번에서 세운 프레임(판독 → 링크 분류 → 오프셋 유도 → payload 조립)이 외부 개입 없이
한 사이클 돌았다.** 3일차의 결과다.

문제 구조: 링크 ② 를 canary 가 막고, ④ 는 다시 ret2win. **②를 우회한 것이 아니라 통과했다** —
값을 알면 `__stack_chk_fail` 은 애초에 불리지 않는다.

## 9. ⭐⭐ "배열 크기 + 8" 은 공식이 아니라 우연이었다

그가 물은 패딩의 정체가 이 세션의 최대 수확이다.

canary 는 **항상 `[rbp-8]`** 이고, 큰 지역 배열은 **16바이트 정렬** 위치에 놓인다. 그래서
64바이트 배열이 `rbp-0x48`(8정렬, 탈락)이 아니라 `rbp-0x50`(16정렬)에 배치되고, 배열 끝과
canary 사이에 **아무도 쓰지 않는 8바이트 구멍**이 남는다. 복귀 주소까지의 거리는 72가 아니라
**88**이다.

이전 세 문제에서 공식이 통한 이유: canary 가 없어서 `sub rsp, N` 의 `N` 이 배열 크기와
**우연히 일치**했다. 전제가 명시되지 않은 채로 3회 성공했던 것이다.

> **`sub rsp, N` 과 `lea rax, [rbp - M]` 두 숫자가 진실이다. 소스의 `[64]` 는 힌트일 뿐.**

⭐ 그리고 이것은 **정렬이 두 종류**라는 뜻이기도 하다 — `Stack_Alignment` 의 `rsp` 16정렬(ABI,
`call` 시점)과 프레임 **안** 객체의 16정렬(컴파일러 배치). 둘 다 16이라 혼동하기 쉽다.

## 10. 링크 ⓪ 의 정의를 같은 날 두 번 고쳤다

오전에 ⓪ 를 **"주소 확보"** 로 정의했다. 오후의 문제에서 payload 에 넣어야 했던 값은
**주소가 아니라 canary** 였다.

> ⓪ = **런타임 비밀의 확보.** 인스턴스: 스택 주소 · libc base · PIE base · **canary**.

🔴 **정직하게: 첫 정의가 너무 좁았다.** 한 사례(ret2libc)에서 일반화했기 때문이다. 같은 날
반례가 나온 것이 운이 좋았다 — 노트에 굳었으면 한동안 틀린 프레임을 들고 다녔을 것이다.
**교훈: 링크를 새로 만들 때는 그 링크가 담는 것을 *한 사례의 타입*으로 이름 붙이지 마라.**

## 11. canary 값 자체에서 읽은 것

유출값이 `0x…00` 으로 끝났다. glibc 가 **의도적으로** 최하위 바이트를 NUL 로 만든다 —
리틀엔디안이므로 메모리상 첫 바이트가 NUL 이고 `strcpy`/`puts`/`%s` 가 거기서 멈춘다.
canary 가 자기 유출 방어를 스스로 들고 있다.

대가: 실효 무작위성 **7바이트(2⁵⁶)**. fork 서버라면 바이트 단위로 최대 1792회에 뚫린다.
그리고 그 brute force 가 성립하는 근거는 `fs:0x28` 이 **스레드당 하나**이고 `fork` 가 그것을
**상속**한다는 사실이다 (`execve` 는 새로 뽑는다).

## 12. 부수 지식 — `_exit` 는 flush 를 건너뛴다

출제자 코드가 `fputs(flag, stdout); _exit(0);` 인데, `_exit` 는 `FILE*` 버퍼를 비우지 않는다.
앞쪽의 `setvbuf(stdout, NULL, _IONBF, 0)` 가 그것을 막고 있다 — **두 호출이 짝**이다.
파이프로 붙였을 때 출력이 사라지는 현상의 전형적 원인.

## 14. 3일 궤적 정리

```
BOF 1  ret2win                 ④ = 선물 함수
BOF 2  ret2shellcode           ④ = 주입 코드        (NX 꺼짐이 전제)
BOF 3  ret2libc / ROP          ④ = libc 함수        (NX 켜짐이 강제)
BOF 4  canary + ret2win        ② 통과 + ④ = 선물 함수
```

⭐ **네 문제 모두 ⓪ 를 출제자가 제공했다** — `%p` 버퍼 주소 / libc 주소 / canary.
**다음 단계는 ⓪ 를 스스로 만드는 것이다** (ret2plt 2단계 leak, format string). 그것이
실전의 시작점이고, 이 세트가 가르치지 않은 유일한 부분이다.

- 배포 libc 로 로컬 재현 (`LD_PRELOAD` / `patchelf`) 미학습
