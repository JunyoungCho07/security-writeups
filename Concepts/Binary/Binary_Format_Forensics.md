# Binary Format Forensics

> [!tip] Lite note — session-explored, **not** a full 15-step atom.
> 이 세션의 **방법론 본체**. 개별 포맷 지식이 아니라 "어떤 포맷에도 적용되는 절차"만 남긴 것.

## Definition (Formal, EN)

Binary format forensics is the systematic comparison of **declared** values (metadata a
file states about itself) against **measured** values (properties derived from the file's
actual bytes). A file is tampered iff some declaration contradicts a measurement or a
normative constraint of its specification.

## Intuition (KR)

헤더는 뒤따르는 데이터를 **설명**한다. 조작된 파일은 **설명과 대상이 어긋난다.** 그래서 하는 일은 언제나 같다 — 선언값과 실측값을 나란히 놓고 대조하는 것.

## Key Points (무엇을 팠나)

### A. 어긋날 수 있는 축은 다섯뿐이다
포맷을 가리지 않는다. 컨테이너 구조를 쓰는 어떤 파일에도 그대로 적용된다.

| # | 축 | 대조 방법 |
|---|---|---|
| 1 | **정체** — 시그니처가 실제 내용과 다르다 | 시그니처 vs 뒤따르는 바이트의 성격 |
| 2 | **길이** — 선언 길이 ≠ 실제 데이터 길이 | 레코드 체인 순회. 어긋나는 지점이 답 |
| 3 | **무결성** — 체크섬 ≠ 재계산 값 | 다시 계산해서 비교 |
| 4 | **구성** — 있어야 할 게 없거나, 없어야 할 게 있다 | 규격의 필수/순서/개수 규칙과 대조 |
| 5 | **정합성** — 필드 값끼리 물리적으로 모순 | 값 A로부터 B를 계산해 실제 B와 비교 |

**축 5가 가장 강력하다.** 축 1~4는 "규격 위반"을 잡지만, 유효한 값을 다른 유효한 값으로 바꿔치기한 조작은 규격을 통과한다. 축 5는 규격이 아니라 **데이터 자체**와 대조하므로 그것도 잡는다.

### B. 판을 좁히는 질문 둘 (돈 안 드는 것부터)
- **파일이 정상적으로 열리는가?** 열린다면 디코더가 *무시하는 자리*에 이상이 있다(관대한 파서는 모르는 요소를 건너뛴다). 안 열리면 디코더가 거짓말에 *부딪힌* 지점이 곧 위치 정보다.
- **규격이 설명하지 못하는 잔여 바이트가 있는가?** 종료 표시 오프셋 + 규격상 뒤따를 바이트 수 vs 파일 크기. 산수 한 번이다.

### C. 오라클 설계 — 이 세션의 가장 큰 수확
> **검사를 하나 추가하는 비용은 한 줄, 얻는 것은 가설의 소거다.**

- 오라클은 "코드가 맞았나"만 알려주는 게 아니라 **가설 하나를 통째로 죽인다**. 예: 레코드 체인이 파일 끝에 정확히 착지했다는 사실은 순회 정확성뿐 아니라 *"길이 필드가 조작되었다"는 가설*을 배제한다.
- **독립된 두 방법이 같은 답을 내면 둘 다 맞은 것이다.** 도구가 다르면 실패 모드도 다르므로 우연히 일치하기 어렵다.
- 규격이 `shall`로 강제한 불변식은 그대로 `assert`가 된다. 위반 시 **조용히 진행하지 말고 즉시 멈춰라** — 틀린 상태로 이어간 계산은 겉보기엔 멀쩡한 쓰레기를 낸다.
- assert의 자리: 검사 대상 값이 **만들어진 직후, 그 값을 쓰기 직전**. 슬라이스 뒤에 두면 이미 잘못된 슬라이스가 실행된 뒤다.
- ⚠️ **동어반복 assert를 조심하라.** 도구 X의 출력을 상수로 옮겨 적고 X와 비교하면 항상 통과한다. 검증이 성립하려면 상수가 **독립된 출처**(명세서, 카탈로그, 직접 구현)에서 와야 한다.

### D. 검출 ≠ 위치 특정
- 체크섬은 "레코드 어딘가가 어긋났다"까지만 말한다. **어느 바이트인지는 원리적으로 담을 수 없다** — N바이트의 상태를 4바이트로 요약했으니 위치 정보가 소실된다.
- 위치를 좁히는 것은 **규격 제약**이다. 각 필드마다 독립적인 허용값이 걸려 있으므로, 위반한 필드가 곧 위치다.
- 불일치의 원인은 항상 셋이다: 덮인 범위가 바뀜 / **저장된 체크섬 자체가 바뀜** / 길이 필드가 바뀌어 덮는 범위가 달라짐. 증상이 동일하므로 하나씩 배제해야 한다.

### E. 제약의 폭 = 조작 탐지력
> **제약이 좁은 필드는 조작이 즉시 드러난다. 제약이 넓은 필드는 조작해도 규격 검사를 통과한다.**
> 그래서 값을 숨기려는 쪽은 **넓은 필드**를 고른다.

허용값이 하나뿐인 필드(예: "only method 0 is defined")는 건드리는 순간 파서가 거부한다. 반면 "0만 아니면 된다" 류의 필드는 21억 가지 값이 전부 합법이다. **후보를 좁힐 때 이 폭을 먼저 세어봐라.**

### F. ⭐ 판정자를 매수하지 마라
조작을 되돌린 뒤 **체크섬을 재계산해서 덮어쓰면 안 된다.** 그러면 어떤 값을 써넣어도 통과하므로 검증 능력이 0이 된다.

- 조작자가 체크섬을 갱신하지 **않았다면**, 저장된 값은 *원본* 체크섬이다. 원래 값으로 되돌리면 **저절로 일치한다.**
- 그 일치는 크기 정합성보다 강한 증거다: 크기 검사는 "그 값이 모순되지 않는다"까지고, **체크섬 일치는 "그 값이 원본에 있던 바로 그것"임을 증명한다** (1비트만 달라도 완전히 다른 값이 나오므로).

### G. 명세서 읽기 — 이것 자체가 기술이다
- **조동사가 강도를 정한다.** `shall`/`must` = 강제(위반 시 규격 부적합), `should` = 권고, `may` = 허용. **`shall` 문장만 assert로 옮겨라.** `may` 문장을 assert하면 정상 파일이 튕긴다.
- **반복되는 명사구는 정의된 용어다.** "PNG four-byte unsigned integer" 같은 표현은 영어가 아니라 규격이 따로 정의한 용어 — 정의 절을 찾아야 엔디언 같은 파라미터가 나온다.
- 신뢰 순서: **공식 명세서 > 레퍼런스 구현 소스 > 위키 > 블로그.** 함정(무엇을 세는가·덮는 범위·엔디언)은 1번에만 정확히 적혀 있다.
- **목차부터 봐라. 통독하지 마라.** 필요한 절은 보통 2~3개다. 표를 먼저 만들고 그 칸만 채워라 — 읽는 것과 손에 쥐는 것은 다르다.
- HTML판을 선호(검색 가능). 배치도(figure)가 본문 세 쪽보다 낫다.

### H. 도구 역할 분담
| 도구 | 맡는 일 | 맡기면 안 되는 일 |
|---|---|---|
| **직접 짠 파서** | 전수 순회·모든 필드 추출·계산과 비교 | — |
| **헥스 뷰어** | 코드가 **지목한 좁은 구간**을 눈으로 확인 | 파일 전체 훑기 |
| **명세서** | 필드 표·파라미터 확보(한 번 읽고 코드로 옮김) | 반복 참조 |
| **규격 검증기** | 내 분석의 **사후** 교차검증 | 먼저 집는 것 — 3초에 끝나고 배우는 건 0 |

**"명세서를 코드로 옮기는 것"이 작업의 본체다.** 명세서의 필드 표는 사실상 파서 소스를 자연어로 적어둔 것이고, 둘은 1:1로 번역된다.

### I. 조용한 실패를 경계하라 — 이 세션에서 실제로 겪은 것들
- **표시용 텍스트를 grep하면 줄 경계에서 끊긴다.** 원본 바이트를 직접 뒤져야 한다(`grep -abo`). "못 찾음"이 "없음"이 아니다.
- **텍스트 모드로 바이너리를 읽으면 개행이 변환된다.** 경고 없이 길이가 줄고 그 뒤 모든 오프셋이 밀린다 ([[Concepts/Linux/File_IO_And_Cursor]]).
- **`bytearray` 슬라이스 대입은 길이를 강제하지 않는다.** 4칸에 2바이트를 넣으면 조용히 크기가 바뀌고 이후 오프셋이 전부 어긋난다.
- 공통점: **에러가 안 난다.** 그래서 매 단계마다 "길이가 여전히 맞는가"를 assert로 못 박는 습관이 필요하다.
